# SalesMesh Fraud Detection System

AI-based anomaly detection that flags fraudulent and colluding sales agents on the SalesMesh onboarding platform, for review by an analyst. This repository holds module U-CS 56 (AI Fraud Detection): the ML pipeline in `ml/`, plus the backend and frontend that serve its results.

## Problem

SalesMesh pays agents a commission per customer activation. That creates an incentive for fraud: fake customers, duplicate activations of the same customer, scripted sequential customer ids, and groups of agents sharing customers (collusion rings).

## Approach

- **Unsupervised anomaly detection**, one score per agent per analysis period. The chosen model, `lof_v3_4f`, is a Local Outlier Factor (`n_neighbors` 50); an Isolation Forest was its closest alternative.
- **Four behaviour features:**
  - `submission_frequency`: busiest 24 hours;
  - `time_of_day_entropy`;
  - `customer_similarity`: how alike the customer ids are;
  - `collusion_score`: share of customers also used by other agents.
- **No label is used in training.** Labels are used only to choose among models on validation and to evaluate.
- **Flagged agents get a plain-language reason.** A flag is a request for human review, not a decision.

## Data (synthetic)

All data is synthetic, generated by `ml/data_generation.py` (seed 42): 1000 agents, 130 of them fraud (13%), 135,494 activation records from 1 to 30 August 2026 (Africa/Nairobi), 47 counties, 20 clients and 12 categories. Files in `ml/data/synthetic/`:

| File | What it holds |
|---|---|
| `agents.csv` | agent id, registration time, county, account status |
| `agent_identity.csv` | fictional name, phone and national ID (never a model input) |
| `agent_categories.csv` | certified and expired categories per agent |
| `activation_records.csv` | one row per activation: agent, time, customer, client, category, status, quality score, commission |
| `clients.csv` | the 20 clients, their categories and commission rates |
| `labels.csv`, `rings.csv` | ground truth, for evaluation only |

The data follows the platform's integrity rules (R1 to R6) for honest agents. Fraud patterns break them on purpose. Details: `ml/DATA_CARD.md`.

## Design: 70/15/15 at agent level

Agents, not records, are split: **700 train / 150 validation / 150 test**, stratified by fraud pattern, seed 42.
- Models and scalers are fitted on train only.
- Every choice (features, model, cutoff) was made on validation, under rules written in advance (`ml/results/selection_rule.md`, `acceptance_criteria.md`).
- The test set was read **once**, after every frozen file had been hashed and checked (`ml/results/FREEZE.md`, `test_read_once.json`).

## Main results

**Headline (stability over 10 independent synthetic datasets, seeds 101 to 110, each with its own split and fit):**
- **PR AUC 0.811 (SD 0.035)**, ROC AUC 0.933 (SD 0.019);
- recall 0.689 and precision 0.748 at a 13.3% alert rate.

**Seed 42 test set** (150 agents, 19 fraud), read once:

| | PR AUC (95% CI) | ROC AUC | Precision | Recall | F1 |
|---|---|---|---|---|---|
| `lof_v3_4f` | 0.845 (0.684 to 0.960) | 0.953 | 0.600 | 0.789 | 0.682 |
| Best single feature (`collusion_score`) | 0.565 | 0.734 | 0.435 | 0.526 | 0.476 |
| Random scores | 0.140 | 0.474 | 0.104 | 0.126 | 0.114 |

- **Acceptance criteria Q1 to Q6 and S1 to S4 all pass.** Scoring takes 0.06 ms per agent; the model is 0.35 MB.
- **Every ring, sequential and duplicate fraud agent in the test set was flagged; no weak fraud agent was.**
- A simple integrity rule, `duplicate_activation_rule`, reaches PR AUC 0.862 with precision 1.000. That precision comes from how the synthetic data was generated, so it is a ceiling, not a real-world estimate.

Full write-up: `ml/results/FINAL_TEST_RESULTS.md`.

## Limitations

- **Synthetic data only.** These results cannot show performance on real SalesMesh agents.
- **Weak fraud is missed:** agents who are fraudulent only 10% to 25% of the time look normal (0 of 4 caught on test).
- **Small evaluation sets** (19 to 20 fraud agents), so the intervals are wide.
- **Some patterns separate on one feature** in this data (strong rings, sequential and duplicate fraud).
- **Scores are not probabilities.** The cutoff assumes a 5:1 cost of a missed fraud agent to a false alarm.
- **Process disclosures:** the generator was changed after labelled summaries had been seen (four label-aware changes plus an integrity fix), and the selection rule was amended post hoc on validation. See `ml/results/DEVIATIONS_FROM_PROPOSAL.md`.

## Reproduce, score, retrain

From `ml/`, using the repository's virtual environment (`venv\Scripts\activate`):

```bash
python run_pipeline.py                 # Steps 1-10: generate, clean, split, EDA, features, baselines, models, selection, explanations, system checks
python run_pipeline.py --dry-run       # list the steps without running them
python -m pytest -q tests              # ML tests
python retrain.py --features new_feature_vectors.csv   # refit on new unlabelled agents; cutoff from the validated alert rate
```

Scoring with the frozen model, in Python from `ml/`:

```python
from scoring import load_bundle, score_agents
bundle = load_bundle("runs/20261013-100433_explain/scoring_bundle.joblib")
scores = score_agents(bundle, features)  # agent_id, period, score, flag, threshold, model_version, top_features, reason
```

Step 11 (`final_evaluation.py`) has already been run and refuses to run again. Details: `ml/README.md`.

## Architecture

- **Data:** PostgreSQL (agents, activation records, feature vectors, fraud flags, review decisions, administrators).
- **Backend:** Flask REST API, session-based auth, SQLAlchemy ORM. The backend's `FraudDetector` loads a saved model and scores agents; detection cycles are scheduled with APScheduler. **The backend still serves the v2 Isolation Forest (`ml/models/isolation_forest_v2.joblib`) and the v2 features.** Moving it to `lof_v3_4f`, the v3 features and the new data is backend-sprint work (`ml/results/CHANGES.md`, change 5).
- **Frontend:** React and MUI dashboard.

## Repository layout

- `ml/`: synthetic data, the ML pipeline, results (`ml/results/`) and run folders (`ml/runs/`); docs `ml/README.md`, `ml/DATA_CARD.md`, `ml/MODEL_CARD.md`
- `backend/`: Flask API, auth, database layer and the live detection pipeline (`src/pipeline.py`, `src/detector.py`)
- `frontend/`: React dashboard

## Backend setup

All backend commands run from inside `backend/`. The virtual environment lives at the repository root.

```bash
python -m venv venv
venv\Scripts\activate          # Windows (macOS/Linux: source venv/bin/activate)
cd backend
pip install -r requirements.txt
```

Create `backend/.env` with `DB_PASSWORD` and `FLASK_SECRET_KEY`. Then, from `backend/`:

```bash
pytest                     # run tests
python -m src.load_data    # load the CSVs from ml/data/synthetic/ into PostgreSQL
python -m src.pipeline     # run the detection pipeline
```
